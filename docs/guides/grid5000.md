# Production builds on Grid'5000

This guide covers the supported bounded streaming workflow. Sentence
segmentation runs only inside an allocated CUDA job. Frontends prepare the
checkout, submit jobs, and inspect durable logs; they never construct the SaT
model or run inference.

The recommended public entry point runs from the Mac with the external project
disk connected:

```bash
uv run osm-polygon-grid5000 run \
  --scope region \
  --region afghanistan-latest \
  --stage all
```

For the worldwide V2 lane, use `--scope all --stage all`. The split output is
kept in its V1 schema, then a separate managed V2 input is built by downloading
the pinned `polygons/{region}.parquet` files from the input dataset and adding
canonical `tiny`, `small`, `medium`, or `large` area fields. This preparation is
idempotent and runs before any V2 labeling allocation. A V2 `--stage label` run
is refused when that enriched input is absent.

It resolves immutable inputs, selects a compatible site, stages the checkout,
submits non-interactive OAR jobs, prints live progress, and resumes validated
checkpoints. The individual scripts below are retained compute payloads for
advanced troubleshooting; normal operation does not require invoking them.

## Prerequisites and storage model

You need a Grid'5000 account, access to a GPU site, an existing Hugging Face
output dataset, and standard Hub authentication in the remote environment.
The scripts never accept a token argument.

Keep the Git checkout, virtual environment, Hugging Face model cache, and logs
on persistent storage. Allocation-local scratch holds only the current input
shard and temporary output. Completed shard checkpoints are verified on the
Hub before local scratch is evicted, so another allocation can resume without
repeating completed work. Never place a dataset mirror on a frontend `/tmp`.

The public operator enforces both shared-resource policies before work begins
and again before every OAR submission:

- it runs `usagepolicycheck -l --sites <site>` and `usagepolicycheck -t`;
  jobs use OAR's `day` type only when their complete walltime fits inside
  weekday working hours, and `night` otherwise; GPU jobs additionally use
  the `exotic` resource type;
- it reads the account's live `/home` quota and treats remaining soft-quota
  headroom as the storage limit, even when `df` reports terabytes free;
- if any reachable site is storage-limited, it reclaims terminal
  operator-managed roots on every reachable site; failed roots with
  `progress.json` or checkpoints, the selected run, active runs, and unrelated
  files are never removed, then the quota is measured again;
- it refuses staging or submission if the required safe headroom is still
  unavailable.

Each compute wrapper recreates `.venv` on the allocated node before invoking
Python. This avoids executing a frontend-built environment on a different CPU
architecture. The environment log is kept with the allocation log, while the
temporary uv cache remains allocation-local.

This follows Grid'5000's
[usage policy](https://www.grid5000.fr/w/Grid5000:UsagePolicy) and
[storage guidance](https://www.grid5000.fr/w/Storage). The default `/home`
soft quota is 25 GB; exceeding the larger hard limit is not treated as usable
capacity.

## Immutable revisions

Pin both identities before submission:

```bash
export INPUT_REPO_ID="NoeFlandre/osm-polygon-wikidata-only"
export OUTPUT_REPO_ID="NoeFlandre/osm-polygon-wikidata-sentence-relevance"
export INPUT_REVISION="<40-character-input-commit>"
export SOURCE_COMMIT="$(git rev-parse HEAD)"
test "$(git rev-parse origin/main)" = "${SOURCE_COMMIT}"
```

`INPUT_REVISION` and `SOURCE_COMMIT` must be lowercase 40-character Git
identifiers. Mutable names such as `main` are rejected by the submission
scripts.

## Frontend preparation

Define persistent directories and install the locked environment from the
clean detached checkout:

```bash
export REPO_ROOT="${HOME}/g5k-sentence-build/repo"
export HF_HOME="${HOME}/g5k-sentence-build/hf-home"
export LOG_ROOT="${HOME}/g5k-sentence-build/logs"
mkdir -p -m 0700 "${HF_HOME}" "${LOG_ROOT}"
git -C "${REPO_ROOT}" status --porcelain
uv sync --locked --extra operator --extra hub --extra segmentation -C "${REPO_ROOT}"
```

The status command must print nothing. Model files may be cached in
`HF_HOME`; input Parquet files are fetched one shard at a time by the compute
job.

## Bounded streaming submission

Choose a stable run ID. `MAX_SHARDS=0` with an empty final shard argument
processes every remaining shard. A canonical `afghanistan-latest` final
argument processes exactly that shard and requires `MAX_SHARDS=0`.

```bash
"${REPO_ROOT}/scripts/grid5000/submit_streaming_build.sh" \
  "${REPO_ROOT}" "${HF_HOME}" "${LOG_ROOT}" \
  "${OUTPUT_REPO_ID}" "${INPUT_REPO_ID}" \
  "${SOURCE_COMMIT}" "${INPUT_REVISION}" \
  "sentence-build-v1" "128" "0" "afghanistan-latest"
```

The adapter submits one non-interactive default-queue job requesting one GPU
with a 30-minute walltime. It selects the current Europe/Paris `day` or
`night` policy window only when the complete allocation fits inside that
window, so a short job can start during the current compliant window.
The compute wrapper verifies the checkout, runs the CUDA preflight, and invokes
`scripts.streaming.driver` with `--device cuda`. It does not fall back to CPU,
MPS, or automatic device selection. The driver downloads at most one shard's
six required Parquet inputs, processes it, uploads and independently verifies
the checkpoint, then evicts local shard data.

## Monitoring and resume

Capture the numeric job ID printed by OAR and monitor it from the frontend:

```bash
oarstat -j "${OAR_JOB_ID}"
find "${LOG_ROOT}/${OAR_JOB_ID}" -maxdepth 1 -type f -print
```

Inspect `build.exit_code`, `gpu_preflight.json`, and the stdout/stderr logs.
Do not edit a checkpoint namespace manually. To resume after walltime or a
transient failure, submit the same command with the same run ID, source commit,
input revision, model, pipeline version, and batch size. Verified remote
checkpoints are reused; mismatched identities fail closed.

## Deterministic finalization

Finalization is a separate bounded job. For a single-region release, set
`EXPECTED_SHARD` to its canonical shard key and use the run-scoped checkpoint
namespace created by the build:

```bash
export RUN_ID="sentence-build-v1"
export STAGING_REVISION=".pipeline/checkpoints/${RUN_ID}"
export EXPECTED_SHARD="afghanistan-latest"
"${REPO_ROOT}/scripts/grid5000/submit_streaming_finalization.sh" \
  "${REPO_ROOT}" "${HF_HOME}" "${LOG_ROOT}" \
  "${OUTPUT_REPO_ID}" "${INPUT_REPO_ID}" \
  "${SOURCE_COMMIT}" "${INPUT_REVISION}" \
  "${RUN_ID}" "${STAGING_REVISION}" "${EXPECTED_SHARD}" \
  "02:00:00" "cpu"
```

The job streams verified checkpoints, performs global deterministic
finalization, and persists `sentences.parquet`, `manifest.json`, and
`README.md` beneath `${LOG_ROOT}/${OAR_JOB_ID}/output/` before allocation
scratch is removed. GPU finalization is supported only when explicitly chosen;
it is normally unnecessary.

## Validation and publication boundary

Validate the persistent output before any publication:

```bash
uv run python - <<'PY'
from pathlib import Path
from osm_polygon_sentence_relevance.output.validation import validate_export_directory

validate_export_directory(Path("/absolute/path/to/job/output"))
print("validation passed")
PY
```

Publication is a separate remote mutation. Publish only a complete, validated
release, then independently download it and validate the readback. The
publisher targets an existing repository, uses one Hub commit, accepts no token
argument, and never creates repositories.

## LLM labeling on Grid'5000

The historical V1 labeling stage consumes the immutable Afghanistan
`sentences.parquet` and adds two independent model labels: land-use/land-cover
relevance and target polygon relevance. V1 remains pinned to its original
`unsloth/Qwen3.6-27B-MTP-GGUF` GGUF model for release reproducibility. The worldwide V2 lane uses the same
runtime but emits one `place_relevance` label per selected sentence. That label
asks whether the target place is described in visual or geographic terms,
covering terrain, landscape, land or water cover, soil, ecosystems, vegetation,
visible structures, and physical geographic setting. V2 emits only `yes` or
`no`; it does not generate JSON, reasons, evidence excerpts, or uncertain
labels. The stored score evidence is the first-token log-probability returned
for each alternative, their margin, and a relative two-class probability. It uses
`ggml-org/Qwen3.6-27B-GGUF` with the pinned
`Qwen3.6-27B-Q4_K_M.gguf` file. Model weights, the base tokenizer, and the
input Parquet must be staged on persistent storage before the job; the payload
does not download large files or run on a frontend.

The production path uses `llama.cpp` directly because it can expose the first
generated token's `yes` and `no` log-probabilities from a GGUF model. The
`llama-server` binary is launched as a real subprocess with the model's public
alias, one generated token, temperature zero, and the validated parallelism is
expressed as the `--parallel` argument. The supported parallelism set is the
small validated set {1, 2, 4, 8, 16, 32}; the payload rejects any value
outside this set before the binary is launched.

### Measured throughput and parallelism

The OAR 334344 canary run (200 representative rows, source commit `bc97892`)
measured ~0.593 rows/second end-to-end with `LLAMA_PARALLEL=16`, which is
~2,135 rows per hour. A full run of 54,462 rows therefore projects to
~25.5 hours of pure inference at this rate. Allowing for model warm-up, the
first-batch latency, occasional repair attempts, and checkpoint write-back,
the conservative estimate is ~30.7 hours.

The canary compared `LLAMA_PARALLEL=2` and `LLAMA_PARALLEL=16` on the same
128-row subset and the higher parallelism did not improve throughput on
this single-GPU node. Do not extrapolate from the canary that the GPU is
saturated or that larger parallelism values (e.g. 32) cannot help; that has
not been measured and may require changing the request concurrency to
match the slot count.

### Allocation plan

The Mac operator runs a sequence of **20-minute allocations**, all reusing the
**same persistent `LABEL_WORK_DIR`** and the **same run identity** (model repo
+ revision, model file + SHA, prompt version, source commit, input revision,
batch size, parallelism, per-slot context, total context, and request
concurrency). Each allocation is submitted with the exact same command:

```bash
"${REPO_ROOT}/scripts/grid5000/submit_worldwide_labeling.sh" \
  "${REPO_ROOT}" "${HF_HOME}" "${LOG_ROOT}" "${INPUT_PARQUET}" \
  "${LABEL_WORK_DIR}" "${LABEL_OUTPUT_DIR}" "${MODEL_FILE}" \
  "${TOKENIZER_DIR}" "${MODEL_REVISION}" "${INPUT_REVISION}" \
  "${SOURCE_COMMIT}" \
  "NoeFlandre/osm-polygon-wikidata-sentence-relevance" \
  "128" "0" "8" "8192" "8" \
  "200000" "sentence-relevance-v2" "3"
```

The final three arguments define the V2 label sample: a target row count, a
stable seed, and the H3 resolution. V2 groups rows by H3 cell, language, and
OSM primary tag, then selects a deterministic proportional prefix. Re-running
with the same input, seed, and resolution and a larger target extends the
earlier sample instead of replacing it. The target is stored as a mutable
continuation budget while the immutable run identity stays fixed; a smaller
target is rejected once the run has been initialized. Use `resume RUN_ID
--sampling-target N` to raise the target without creating a new run. The Afghanistan V1 release and its
published artifacts remain separate and are not changed by this sampling mode.
When a V2 run is published, its manifest-bound publisher writes below
`v2-worldwide/` on the same Hugging Face `main` revision and refuses to replace
the V1 root files.

The next allocation is submitted only when the validated checkpoint still
contains remaining rows. The run is finalized (and the one-commit Hub
publisher is invoked) only by the allocation whose run reaches
`completed == total` rows.
The job wrapper enforces a strict clean-checkout guard: every dirty entry
in the repository except the explicitly-approved `.venv` deployment entry
is rejected before any binary is invoked.

The automatic operator gives inference **10 minutes**, followed by a
**5-minute graceful checkpoint window** and five minutes of scheduler margin.
It passes these bounded values to the same compute-node wrapper. The wrapper
installs a SIGINT handler after the inference budget; if the labeling CLI has
not finished by then, the
handler saves checkpoints and exits successfully with an `interrupted=true`
summary so the next allocation can resume from the same `LABEL_WORK_DIR`.
After the 5-minute grace, the wrapper escalates to SIGKILL and returns
non-zero so OAR records a walltime exit; completed batches remain durable
on the Hub and on persistent storage. Normal early completion cancels the
helper immediately.

The standalone submission adapter uses a **30-minute** walltime (20 minutes
of work and ten minutes for graceful checkpointing). The short allocation is
intentional: smaller jobs are easier for OAR to backfill, and validated
checkpoints make repeated allocations safe.

### Submitting the labeling job

Use the non-interactive frontend adapter. The final argument is the
supported parallelism value (`LLAMA_PARALLEL`); the second-to-last argument
is the row limit. Use a positive row limit for a non-publishing canary and
`0` only for an approved complete run.

The adapter requests one GPU with at least 40 GiB of memory and a 30-minute
walltime. It binds the job to the current Europe/Paris `day` or `night`
policy window, so the job cannot cross a weekday boundary. The payload launches the real
`llama-server` binary directly with `--ctx-size ${LLAMA_TOTAL_CONTEXT}` and
`--parallel ${LLAMA_PARALLEL}` (where `LLAMA_TOTAL_CONTEXT` is computed as
`LLAMA_PARALLEL * 4096`). It accepts the server only after both the health
endpoint and four real, schema-validated labeling requests succeed. The
client concurrency is pinned to the parallel slot count so the request stream
cannot outpace the server's bounded slots. The selected engine,
parallelism, per-slot context, total context, and request concurrency are
recorded in the run identity and persisted in the manifest, so a resume
cannot silently change servers. The production code does not rely on
`sitecustomize`, `PYTHONPATH` overrides, monkey-patching, or wrapper
binaries. There is no vLLM attempt, no CPU or MPS fallback, and no
frontend-side inference.

Each batch undergoes one bounded repair attempt when the model response
fails the strict validation contract: the runner retains the original prompt
context, tells the model the exact rule that failed, and validates the
replacement against the same strict schema. The timing summary records
`initial_inference_seconds` and `repair_inference_seconds` separately so the
inference budget can be audited; their sum is published as
`inference_seconds`. Repair counts are tracked factually; raw prompt and
response content are never written to public logs.
Validated label batches are atomically checkpointed after every batch. SIGINT
or SIGTERM stops new work, preserves completed batches, writes factual progress
and timing, and permits the same command to resume. Progress reports completed
and remaining rows, throughput, elapsed time, and ETA. A positive row limit
creates and validates a canary output but never publishes it. It deliberately
covers both sources and then maximizes language variety with stable hash
ordering, while preserving selected rows in their original order.
The payload also mirrors each completed batch asynchronously to
`.pipeline/checkpoints/<run-id>` on the output dataset's `main` tree. The local
checkpoint is written first and remains authoritative. One worker commits the
batch Parquet and metadata together, so the labeling loop does not wait for Hub
network calls.
Upload failures leave a mode-restricted outbox under
`${LABEL_WORK_DIR}/.checkpoint-mirror/pending/`; the next allocation retries
those markers before processing new rows. The bounded drain at allocation exit
is best effort, and the final release publisher still validates and publishes
only the complete local result to the V1 root or the V2 `v2-worldwide/` path on
the protected `main` revision.
Finalization automatically derives a concise README, label counts,
percentages, reason distributions, language statistics, plots, hashes, model
provenance, server configuration, runtime, throughput, and the completed
allocation count from the labeled Parquet and the persisted timing JSON.
Only a full run (`ROW_LIMIT=0`) reaches the one-commit Hub publisher.

### Hardened Hub publication

The publisher issues exactly one `create_commit` per release containing the
validated Parquet, manifest, README, and deterministic PNG assets. V1 files
stay at the historical root; V2 files are mapped below `v2-worldwide/` in the
same `main` tree. Legacy obsolete artifacts, including the old raw slice HTML,
are deleted only when explicitly allowlisted. The publisher refuses to publish
when the remote tree contains any other unexpected file. `.gitattributes` is
preserved across releases. After the commit, the publisher downloads the
immutable revision and re-runs the publication validator on the readback; the
Parquet SHA-256 and row count must match the local validated publication
exactly. Publication only targets the `main` revision; no token, no branch
creation, and no repository creation are accepted.

## Failure recovery and cleanup

- A non-zero job exit preserves logs and any verified remote checkpoints.
- Reuse the same run identity to resume; use a new run ID for different inputs
  or code.
- Never run inference on a frontend or local Mac as a fallback.
- Remove allocation scratch only through the guarded job wrapper. Delete old
  checkpoint namespaces only after the final release has been validated and the
  deletion has been explicitly approved.
- Persistent caches and logs may be removed when no longer needed; never delete
  an active job's directory.
